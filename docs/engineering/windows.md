# Native Windows implementation

English | [简体中文](../zh-CN/engineering/windows.md)

## Technology decision

Use C#, .NET 10 LTS, WPF with its Fluent theme, and MVVM presentation state. Keep rules, exclusions, scan orchestration, plans, execution state machines and receipts in the existing Swift core. The Windows UI accesses the bundled `shou.exe` through a versioned JSON process protocol. Win32/COM belongs to platform adapters; C# does not duplicate the rule engine.

The Zhiban project informs the native UI separation, structured process bridge and real subprocess tests. Shou independently implements file identity, cleanup consent, Recycle Bin operations and restoration. Its Windows product does not require Zhiban's mathematics reader, WebView2, Python, receiver or model integration.

The initial validation target is Windows 11 x64. ARM64, older Windows releases, network volumes, cloud placeholders and cross-volume operations require separate evidence.

The reviewed Zhiban practices were `AgentProcessClient.cs` (argument arrays, simultaneous pipe draining and bounded strict JSON), `WorkspaceClient.cs` (capability discovery), `zhiban_io.c` (native locking and durable records), and its Windows acceptance document. That project also separates macOS cross-build evidence from Windows runtime and distribution acceptance.

## Filesystem and safety

Preserve the volume serial number, full 128-bit File ID and owner SID. Do not truncate Windows identity into POSIX inode/UID fields. Keep old macOS records readable, and exclude Windows identity from the macOS remount compatibility rule. Record storage requires a private current-user ACL, stable process locks, atomic replacement and durable writes.

Never follow junctions, symbolic links, mount points or unknown reparse points, or hydrate cloud placeholders. Permission errors and exhausted traversal budgets produce partial evidence, which cannot authorize an incompletely measured target.

The first adapter rejects case-sensitive directories rather than pretending their names are case-insensitive. It accepts fixed local drive paths, and refuses UNC/device paths, alternate data streams and reserved device names. System locations, user-profile roots, sensitive directories, configured OneDrive roots and Shou records are protected.

Ordinary AppData root registration is limited to exact bundled cache roots. Those mutation grants cover only the bundled rules' cache subtrees and their descendants; browser profiles, VS Code user data and arbitrary personal rules cannot expand this access. The separate application-data service receives exact grants for maintained personal-data roots and requires independent consent. Cache root matching and binding reuse preserve Windows path casing/separator equivalence. Discovery and fair target budgets use the same algorithm as macOS, with platform-specific no-follow reads. Incomplete matched directories can be continued independently; their new evidence replaces only the selected directory in the UI.

Windows declares 23 fixed locations for Chrome, Chromium, Edge, Brave, Vivaldi, Firefox, Slack, Discord, Notion, Obsidian, GitHub Desktop, Insomnia, Postman, VS Code, VS Code Insiders, Cursor, npm, pip, Gradle, NuGet, Cargo, Yarn and uv, plus 16 shared project rules. Only named cache subdirectories in default user locations are included. Browser profiles, chat/workspace data, editor user data, credentials, installed tools and development environments are retained. Custom data locations, other distribution channels and undeclared applications are not implied coverage. Application cache cleanup also requires activity evidence for the corresponding Windows executables; missing mappings or failed process inspection remain blocking facts.

The four additional locations use [reviewed Windows source references](windows-cache-sources.json). Chromium includes only `Default` / `Profile *` rendering and network cache directories. Obsidian, GitHub Desktop and Insomnia include only top-level `Cache`, `Code Cache` and `GPUCache`; IndexedDB, local/session storage, vaults, repositories, request databases, responses and plugins remain outside mutation grants. Chrome and Chromium share `chrome.exe`, so either process conservatively blocks both cache rules. Figma remains deferred: its current Windows instructions refer to `DesktopProfile` and warn about losing offline changes, which does not establish a safe cache-only boundary.

Project cleanup checks Git tracking through a standard local Git installation and checks build process activity using native process identities and verified working directories. Git runs with bounded pipes, a deadline, a job object and sanitized Git environment variables; it is never resolved through the workspace or PATH. Unreadable process parameters, missing Git in a repository, changing evidence or unsupported process layouts remain blocking facts. Native Windows runtime acceptance of these adapters is still outstanding.

A failed Recycle Bin operation must not fall back to permanent deletion. Restoration must not overwrite an existing destination. Revalidate tree and identity evidence before mutation, journal intent first, and persist the observed outcome. Unknown outcomes remain unknown and are not automatically retried. Windows race boundaries, recycle receipts and system behavior require native validation.

Recycle Bin and restoration stay disabled by default. An explicit `SHOU_WINDOWS_EXPERIMENTAL_RECYCLE=1` process setting is accepted only for isolated native validation; it is not a user-facing production toggle. Permanent removal is enabled by default. The cleanup page offers separate Recycle Bin and permanent-delete buttons, and history offers restoration plus separately confirmed permanent removal of recorded Recycle Bin items when a validated Recycle Bin session is enabled. Every mutation still requires a current scope review. Permanent removal is irreversible.

Permanent removal verifies the complete manifest, pins all reviewed objects with native handles, and checks the original volume, full File ID, SID and metadata before any deletion. It removes known members from children to parents with `SetFileInformationByHandle`, without recursive wildcard deletion. Only a direct parent's timestamps/size are refreshed after removing its own reviewed child; other metadata remains checked. New children stop directory removal. Recycle Bin purge also pins and removes only that item's paired `$I` metadata record. Partial removal retains an unknown/pending journal state and blocks replay.

## Desktop process protocol

The desktop bridge uses the shared core without fabricating terminal input or adding a global `--yes` switch. Confirmation binds an operation, plan or receipt digest, exact selection, one-use challenge and expiry within the same process. Changes invalidate consent. Public CLI mutation keeps its interactive current-scope terminal review.

Use a bundled absolute executable path, argument arrays, UTF-8 JSON, bounded input/output and structured errors. stdout is protocol-only; stderr is drained concurrently with bounded retained diagnostics. Read requests may terminate their owned process on cancellation or timeout. Mutations request cooperative cancellation and stop at item boundaries with durable receipts. A timeout does not prove that nothing changed.

Requests are one JSON line with `bridge_version: 1`, a unique `request_id`, `operation` and object `input`. Events contain the same version/ID, `kind` (`progress`, `confirmation`, `result`) and `value`. Result values retain the public CLI `api_version: "1.0"` envelope. Consent carries the challenge and digest from the current review; cancellation and EOF invalidate it. Input is limited to 1 MiB, one event to 8 MiB and client output to 64 MiB. Confirmation expires after 120 seconds.

Connected operation groups include capabilities/configuration, workspace registration, `system.scan`/`system.clean`, `scan`/`scan.results`/`scan.target`, plans, paged history and follow-ups, personal rule preview/import, `rules.set`/`rules.location-set`, exclusions, and storage scan/directory/page/map/context/remove. `storage.large-files` provides query-bound cursors, size/type filters and per-file removal protection; the WPF large-file page shares the existing storage removal plans, exact confirmation and receipts. Candidate pages contain at most 100 items; large-file pages contain at most 500. Removal plans accept at most 5,000 explicit paths, matching the shared macOS core. The bridge remains an internal transport; public CLI terminal confirmation is independent.

`locations.scan` is a metadata-only inventory of automatically discovered projects, extra included folders and present built-in cache roots, with availability and a configuration revision. The WPF Scan Scope page supports search, source filters, folder inclusion and copying paths. Only extra folders can be stopped with `workspace.remove`: one-use confirmation binds the folder and reviewed revision, and the store lock checks the revision again. Unregistering detaches its bindings, presets and workspace exclusions while retaining files, rule definitions, other workspaces and cleanup history. Automatic locations and built-in caches remain managed by discovery.

`storage.browse` returns up to 200 directory items with the shared core's current removal reasons; the initial `storage.scan` response is also paged. Name search filters every immediate child before paging, treats wildcard punctuation literally and binds continuation to the scan, directory and query. `storage.selection` is read-only and reuses macOS parent/child normalization, including preserving siblings when a covered child is unchecked. Paths and resulting selections are limited to 5,000; excessive expansion is refused without publishing a truncated set. WPF shows partial checkboxes and deduplicated selected capacity, keeps selection across navigation and filters, and resets it for a new scan. Back/forward history commits after the directory loads; breadcrumbs, parent navigation, explicit paging, selecting visible eligible items, copying paths, Explorer selection and coverage details are connected. Map-only nodes stay unselectable until their directory protection has been read. Browsing and selection grant no execution authority; existing fresh manifests, confirmation and receipts still govern removal.

Space and large files share a Scan coverage details window. `storage.scan`, `storage.show` and `storage.large-files` return the same saved scan ID, root, status, entry count, raw issues and typed coverage notes; filtering and paging preserve this metadata. The window distinguishes read failures, changes during scanning, cloud placeholders, other volumes and resource limits. An incomplete scan without reasons remains explicitly unknown. System-managed locations are hidden by default and can be shown without changing permissions. Copying accepts only exact relative paths inside the saved root; Explorer selection is available only for non-system read failures. Escaping paths, aggregate counts and legacy diagnostics with appended error numbers remain visible without exact-path actions. Rescan this scope always uses the displayed saved root. Viewing or closing the window does not change selection or authorize cleanup.

`scripts/verify-storage-coverage.py` checks complete scans, real budget truncation, filtering and paging with generated files, comparing saved records and payload hashes. Regular host tests and Windows Check run it. The bilingual package probe adds complete, partial, missing-reason and system-filter layouts and reports `storage_coverage_layout_loaded`. Package probes and native Windows interactions still require runtime acceptance.

`storage.preview` reads one exact saved-analysis item without mutation confirmation. UTF-8/UTF-16 text is limited to a 256 KiB prefix; PNG/JPEG/GIF/BMP images are limited to 4 MiB, with bounded WPF decoding dimensions. PDF, Office/ODF, RTF, common audio/video and TIFF/WebP/HEIC return a scan-bound `system_preview` descriptor. Directories, executables and other unsupported formats retain scan-snapshot metadata. Space analysis and large files share the preview window; large files also support path copying and Explorer selection. Preview content is not exposed to AI investigation tools.

WPF hosts the registered Windows `IPreviewHandler` in an owned `--native-preview-worker` process or COM surrogate. The worker validates the parent PID/HWND, resolves only a declared PreviewHandlers registration, and pins the reviewed file and ancestors using full identities and read-only handles that deny replacement and concurrent writing. It prefers `IInitializeWithStream` and supports file-only handlers while retaining the same pins. It never executes a file association command. Startup has a 10-second deadline; ready previews stay active until closed. Closing cancels the owned worker, and unavailable components or failures retain file information. The installed provider determines actual format support and rendering behavior; this is not verified Quick Look parity.

`scripts/verify-windows-preview.py` checks real worker input/host/path/format/size boundaries without opening the record store. Windows Check also builds and runs `shou-windows-preview-checks` against generated streams; it never activates an installed preview provider. The bilingual release probe creates and releases a hidden native preview surface. Real Windows provider rendering, keyboard focus, screen readers and SDK execution remain unverified.

Cleanup, space analysis and large files share a disk-capacity view. `GetDiskFreeSpaceExW` reads the actual directory's volume, retaining mount-point and current-user quota semantics; scan totals are not used as volume capacity. Cleanup shows the selected workspace's disk (the user profile disk before selection), space analysis follows the current directory, and large files follow the last successfully applied scan root. Refresh happens when a view loads, its directory changes, the application becomes active or a cleanup completion changes, with a manual refresh action. Reads run outside the UI thread, discard obsolete results and serialize refreshes per view. Missing or unavailable capacity is explicit, and moving files to the Recycle Bin is not represented as released space.

`cleanup.review` projects the same `CleanupReview` used by macOS. It groups categories, rules and directories, resolves overlapping roots and continued-directory evidence, and exposes selectable/recommended counts with attributed capacity. Search, category/rule scope and recommended-only filters page 500 sources at a time; continuation offsets bind to the scan IDs, refinements and query digest. WPF maintains concrete selections independently of visible pages and filters, including three-state group selection and total selected capacity. High-risk, incomplete and otherwise blocked evidence is excluded from recommendations. The projection grants no execution authority; `system.clean` still creates and revalidates plans and rejects overlapping selections.

Candidate rows expose Explorer selection, path copying, space analysis, the existing AI review page and directory exclusion through both a row context menu and keyboard-accessible buttons. Actions use that row's exact root and relative path; exclusion is scoped to its source workspace, independently of the workspace selected in the page header. Exclusion clears the old cleanup review and requires a fresh scan. Opening the AI page does not start a network request. Space analysis now offers separate Recycle Bin and permanent-delete buttons through one receipt-handling flow: only successfully processed items leave the view. Recycle Bin remains capability-gated and disabled by default; a failed recycle operation never falls back to permanent deletion.

Default Windows space measurement streams native directory cursors into a private SQLite catalog, without the deletion-manifest entry cap. Only a bounded page of directory work is loaded at a time; immediate siblings are indexed before descent. The full 128-bit File ID, volume and owner SID survive serialization, and hard links deduplicate by full object identity. Read errors, reparse points, directory changes, depth/time limits and cancellation preserve explicit coverage gaps or abort publication. File removal review hashes large files incrementally with bounded memory, cancellation and a deadline; it does not inherit the 16 MiB metadata-file read limit. Native runtime acceptance remains outstanding.

## Completion and retry parity

The WPF completion overlay follows the shared desktop contract. A successful cleanup shows the completion icon, measured bytes when the receipt provides them (otherwise the processed count), a short outcome sentence and `Done`. It does not force a History visit. Partial, cancelled, failed or verification-blocked receipts additionally show processed, skipped, failed and needs-verification counters, collapsed item details, `Rescan`, `View History` and `Close`. Rescan clears the stale candidate page and performs a fresh scan before a new plan is created; it never replays the previous plan. The overlay and receipt fields are intentionally aligned with the macOS `CleanupResultView` so a CLI or agent can reason about both clients from the same states.

History now keeps each item's identity, allocated size and restore/purge eligibility. Nothing is selected initially; users can select individual items, select eligible items or clear the selection. Confirmation receives exactly the selected IDs, with a maximum of 500 per request. An empty, oversized or mixed-ineligible selection is refused as a whole. Changing records or refreshing receipts clears the selection; loading another page preserves the current record. Application-uninstall purge restrictions and unfinished-action blocks remain in the shared core.

`history.inspect` exposes the existing shared, read-only position check with one execution ID and an optional strict scan budget. The WPF dialog shows exact original/recorded Recycle Bin paths, content matches, changed or missing objects, restore conflicts, unfinished follow-ups and unavailable observations. It can be checked again or closed to cancel the owned read. Inspection never rewrites receipts, retries mutations or grants new eligibility. Package verification includes populated history layouts, selection reset and the inspection dialog; this still requires native Windows UI acceptance. Cleanup, space, extension and large-file size columns sort by raw bytes, and extension percentages sort by their numeric ratios.

The history page's Clean Scan Records action first reads `records.preview` and displays the candidate count, estimated record bytes and retained derived records. Empty previews and verification issues disable collection, and Cancel is the default action. Confirmation calls the existing `records.collect`, which re-evaluates eligibility under the store lock. Active plans, latest scans, cleanup history, recovery data and user files are retained. Interrupted or disconnected collection may have removed some derived records; the UI asks for a new inspection and never retries automatically. Package verification includes populated, empty and blocked preview layouts; Windows UI acceptance remains pending.

## Implementation and acceptance

### Desktop settings and interface language

Settings provides system/Simplified Chinese/English language selection, system/light/dark appearance and reduced motion. Appearance and motion apply after saving; a language change takes effect after explicitly reopening the application, with Cancel as the default and a warning that current selections and unsaved input will be cleared. Reopening is unavailable during active operations or pending AI work. Windows high contrast and disabled system animations take priority without modifying operating system settings.

Presentation preferences use a bounded, versioned JSON file at `%LOCALAPPDATA%/Shou.Desktop/preferences.json`, separate from engine records. Missing preferences use defaults; invalid preferences are reported and can be replaced by saving. Writes use an exclusive temporary file, flush and atomic replacement. Settings displays the engine's actual `configuration.data_directory`, including `SHOU_DATA_DIR`, and links to scan scope, rules, AI, record reclamation, bundled CLI help, documentation, releases, issues and source. Copying CLI help does not launch a terminal or modify PATH. Windows updates still require manually downloading a complete release.

`UiText` resolves application messages and XAML keys through an embedded 1081-message Chinese/English catalog and reuses the shared Chinese/English catalogs for built-in engine messages. Paths, user text and personal rule definitions retain their original content. AI authentication uses fixed identifiers independent of translated labels, and AI investigations and copied space explanations use the selected language. `scripts/verify-windows-localization.py` verifies literal references, XAML keys, catalog completeness and format parameters in regular and Windows checks. The .NET checks cover isolated preference round trips, invalid schemas, failed writes, accessibility precedence, catalog resolution, formatting and stable authentication identifiers.

Release verification launches fresh package probes in both languages, loads the settings page at two window sizes, and exercises all appearance/motion choices. Probes avoid reading or writing saved desktop, AI or space-view preferences. These probes are connected and compile on the macOS host; Windows runtime layout, clipping, keyboard, screen-reader, high-contrast and reopen journeys have not been executed in this stage. Successful compilation and catalog checks do not establish visual acceptance.

### External AI Skill setup

Rules and Settings open the external AI setup window. Codex and Claude Code show their user Skill parent directories, allow an explicit project directory, and provide installation after preview and a request-scoped confirmation. WorkBuddy uses a native save panel to export a ZIP; copying the prepared request preserves the exact bundled Skill/CLI paths and selected workspace. No agent is launched or configured, and no network request is sent. Imported rules remain disabled drafts and require preview, explicit enablement, a fresh scan and separate cleanup consent.

`agent.setup` and `skills.preview` are read-only and do not open the cleanup record store. `skills.install` binds both preview and confirmation to bundled content, the selected client, destination, existing files and the managed-update manifest; it rechecks before publication. Personal edits are preserved and managed old versions receive complete sibling backups. `skills.export` binds consent to the destination and archive bytes and creates a new output exclusively. ZIP creation uses deterministic stored entries with UTF-8 names and CRC32, without a shell or platform archiver. Windows path validation uses the native normalization and reparse-point checks. Cancellation waits for the request to end; uncertain outcomes prompt inspection of the actual destination without automatic retry.

`scripts/verify-agent-setup.py` runs in both regular tests and Windows Check, using only generated client/export directories. It covers strict inputs, cancellation, stale reviews, personal edits, complete backups, exclusive output, ZIP contents/CRC/determinism and linked parents (junctions on Windows). Package probes load all three client choices at two sizes in both languages. Host builds and fixture results do not establish Windows UI interaction, external-client discovery, WorkBuddy upload or terminal CLI installation acceptance. Settings also provides a user CLI command installer, described below; the bundled executable remains usable by its full path.

### User CLI command installation

**Settings → Install CLI Command** previews `%LOCALAPPDATA%/Shou/CLI/shou.exe` and the real bundled engine path, then asks for confirmation with Cancel as the default. It installs only a small native command and its target file, without changing PATH, terminal configuration or system settings. Use the full installed path when the directory is not already on PATH. Keep the complete application at the reviewed location: the command runs the actual `Engine/shou.exe`, so engine updates and adjacent resources stay together. Moving/removing the application requires reinstalling after manually preserving any conflicting command.

The installer checks bounded PE headers and matching x64/ARM64 architecture, hashes the engine and launcher, rejects linked/offline ancestors, and rechecks the reviewed state before publishing a new directory exclusively. Repeated identical installation is unchanged; personal modifications, unknown entries and concurrent destinations are preserved. Cancellation is checked before writes and publication. Paths must be on a local fixed drive. These checks protect normal installation conflicts; they do not isolate another process with the same user's filesystem permissions.

The Win32 launcher imports only Kernel32 and needs no Swift, .NET, CRT, shell or Python beside the installed entry. It reads a bounded UTF-8 `shou.target`, pins the config/engine and ancestors while rejecting reparse points, checks file identity to refuse recursive self-launch, and calls the real engine directly. The original argument tail, working directory, environment, standard streams and exit code are forwarded. A custom parent console handler leaves the child with ordinary Ctrl+C behavior; interactive terminal cancellation still needs Windows acceptance.

Windows Build invokes the official Clang toolchain directly for the launcher and independent argv/stream probe, avoiding SwiftPM’s injected `swiftrt.obj`. Independent C++ fixture targets explicitly link `swiftCore` to resolve that startup object’s runtime import. Check runs `verify-windows-cli-install.py` through the real installer in exclusively generated directories. The native fixture verifies quoting, empty/Unicode/metacharacter arguments, binary stdin, stderr, exact exit codes, resources and junction/conflict refusal. Packaging refuses non-Kernel32 dependencies in the launcher, includes `CLI/shou-cli-launcher.exe`, and the package probes install separate generated entries in both languages before a restricted-PATH version check. Host cross-compilation and .NET checks have passed; official Windows builds, these native fixture executions and WPF installation/console journeys remain NOT RUN.

### Personal rule authoring and revisions

The WPF wizard selects an exact folder or relative patterns, collects size/age/marker/preservation conditions, and presents a read-only preview. Shared `PersonalRuleDraft` constructs the declaration and the sole closed rule parser validates it. Windows case, separators and drive boundaries use the shared path helper after native normalization. Construction neither imports nor enables a rule, and a preview cannot produce an executable plan. Preview counts cover all matching/protected/out-of-condition rows, displays at most 200 rows, and retains partial coverage and issues. Field changes, stopping, version conflicts and stale configuration invalidate saving evidence.

Revision editing exposes complete JSON and a shared-core suggestion for an unused patch version, including metadata editing when the original workspace is no longer registered. Validation preserves the rule ID; import checks the reviewed configuration revision and version uniqueness again under the store lock. New versions remain disabled and existing versions/bindings remain intact. Preview, enablement and a fresh scan still precede cleanup. Export creates a new file exclusively and preserves existing or concurrently created destinations. Built-in rules remain immutable.

The bridge adds `rules.draft`, `rules.validate`, `rules.revision` and `rules.draft.preview`; `rules.import` can require a new version and bind the reviewed configuration revision. `scripts/verify-rule-authoring.py` exercises this chain on generated fixtures in macOS and Windows Check. Windows package verification also loads all three wizard layouts and the JSON editor, which does not replace button journeys or accessibility acceptance.

The rule page filters all/built-in/personal sources. Saving enabled rules asks the shared core to collect the workspace's actual enabled rules under the store lock and verify the configuration revision reviewed by the UI; C# does not recalculate that set. `presets.scan` resolves the stored ID and workspace into a fresh scan. Disabled rules cause refusal rather than enablement or scope expansion. Selections retain rule IDs and use the currently enabled versions, matching macOS.

Exclusions support all workspaces, the current workspace and a project. Projects require an exact relative directory; leaving the pattern empty protects the whole project. Inherited global exclusions are displayed separately and managed in the all-workspaces scope. `exclusions.set` reuses shared validation and rejects invalid explicit scope types, unknown scope fields and projects without a workspace, preventing accidental global changes. Removal uses the exact stored pattern. Changes invalidate old cleanup results. Package verification also loads the rule page in all three exclusion scopes.

### Normal application close and scoped refresh

WPF exposes “Close occupying applications and refresh…” separately from cleanup. `features.close_cleanup_owners` is Windows-only. `cleanup.close-owners` accepts only distinct current `scan_ids` (at most 200), derives owners from blocked candidates and trusted bundled rules, and requires a fresh `applications.close` confirmation listing executable paths and PIDs. CLI `system close-owners --scan-id <id>` uses the same core service and interactive confirmation. Arbitrary process IDs, paths and unattended `yes` input cannot expand the request.

`WindowsCleanupOwnerClosing` and `closing.cpp` bind each selected process to its PID, creation time, current-user SID, nonzero login session, full executable path and complete file identity. The entire selection is checked before an intent is saved, and each target's complete process set is checked again before window messages. Only normal `WM_CLOSE` requests are sent to visible top-level windows in the reviewed processes. Elevated or foreign processes, changed identity and unavailable evidence are refused; save prompts, refusal, background helpers and inaccessible windows remain running. There is no forced termination, privilege elevation or automatic replay. The review expires after 120 seconds, including time spent rechecking; persisted receipts omit executable paths.

After a receipt, WPF synchronously invalidates affected scans, refinements and pagination before any cancellable refresh. It scans only affected workspaces, keeps unrelated evidence and choices, and maps selected paths to fresh eligible sources. Cancellation or failure retains the close outcome and explains that scanning is incomplete. Deletion always requires a separate fresh plan and confirmation.

`scripts/verify-windows-closing.py` checks strict input, platform capabilities and CLI discovery without accepting any real close confirmation. Windows Build also builds the independent C++ `shou-windows-closing-checks` product, separate from the Swift suite affected by the compiler crash. In a standard-user interactive Windows session, run `./scripts/build-windows.ps1 -NativeClosingFixtures` to exercise only exclusively generated `Code.exe` windows: stale identities, whole-selection preflight, cancellation, normal close and refusal. An elevated session returns “not run”, never a successful positive acceptance. Package validation also checks invalidation/retained selection state and populated result layout; neither the native fixture nor WPF probe has been executed on Windows in this stage.

### Tool-managed storage

`NativeCleanupTools` now selects a Windows adapter for Docker, Conda and rustup; Homebrew remains macOS-specific. ### Registered installer uninstall

Existing Windows CI now includes synthetic AI contracts in its Check stage; this revision still requires native CI and UI acceptance.
