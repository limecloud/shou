## UC01：首次发现项目空间占用

**参与者**：用户、Shou GUI、系统授权面板、扫描引擎。

**前置条件**：应用已启动，尚未添加工作区。

**主流程**：

1. 用户选择“添加工作区”，通过系统文件面板选择开发目录。
2. 应用显示将访问的目录和排除设置，不要求先授权整块磁盘。
3. 用户启动扫描，随时可以取消。
4. 应用按项目和目录展示空间占用，区分规则候选项与“待判断”目录。
5. 用户进入目录详情，查看路径、大小、项目标记和发现依据。
6. 对未知的大目录，用户选择“为此目录建立规则”或“始终排除”。

**异常与边界**：

- 没有权限：显示受影响路径与重新授权入口，已有可读结果标为部分扫描。
- 目录消失：记录跳过，不把错误当作零占用。
- 符号链接：首版不跟随，显示跳过原因。
- 扫描取消或部分失败：说明覆盖缺口；不完整候选不能进入计划，独立完整且符合策略的兄弟目标仍可保留资格，旧记录缺少覆盖证据不能放宽。

空间浏览使用完整模式；清理快照须明确其规则扫描范围与稀疏性，不能当作总占用视图。

**后置条件**：获得只读空间视图，尚未执行文件移动或删除。

## UC02：处理闲置 Rust 项目的构建目录

**参与者**：开发者、规则引擎、扫描与计划服务。

**前置条件**：用户已授权工作区，存在多个含 `Cargo.toml` 的项目。

**主流程**：

1. 用户启用 Rust `target` 模板，查看“重新构建可能耗时、依赖离线可用性需自行确认”的说明。
2. 用户设定“目录内最新修改至少距今 14 天”和最小占用，并排除当前工作项目。
3. 引擎结合 `target` 路径与其父目录的 `Cargo.toml` 匹配。
4. 应用展示具体命中目录、条件证据与占用估计。
5. 用户选择本次目录，生成计划并确认移到废纸篓。
6. 执行前复核对象；状态改变或已检测到活动的项目被跳过或使计划失效。
7. 应用记录逐项结果；用户可保存这组规则和排除条件为方案。

**异常与边界**：

- 自定义 `CARGO_TARGET_DIR`：普通模板不会猜测，用户需建立经过验证的个人规则。
- `target` 中有用户手工放入的文件：模板无法证明其可重建，界面必须展示范围并要求用户判断。
- 年龄无法完整计算：该目录不通过年龄条件，不能按“很久未使用”处理。
- 活动检测无发现：不等于可以证明项目没有构建进程；仍需身份与状态复核。

**后置条件**：只有已确认且复核通过的目标被处理，源码不在清理范围内。

## UC03：为自研软件创建个人规则

**参与者**：自研工具作者、规则编辑器、校验与扫描引擎。

**前置条件**：用户知道自研工具产生的某个目录用途。

**主流程**：

1. 用户在空间视图中选择一个未知目录，点击“建立规则”。
2. 向导要求确认该目录用途、可重新生成的条件和需要保留的内容。
3. 用户选择精确相对路径或受限模式，绑定当前工作区。
4. 用户设置保留时间、最小占用和排除项。
5. 应用校验路径边界、格式、风险与资源预算。
6. 用户查看预览；未命中时显示具体条件原因。
7. 用户保存并显式启用规则。

**替代流程**：用户在高级编辑器中粘贴 AI 生成的 JSON，仍执行同一套验证与预览。

**异常与边界**：

- 用户无法确认用途：允许保存为禁用草稿，不提供“已验证安全”的标签。
- 指向凭据、数据库或受保护区域：禁止启用该目标，即使用户规则声明可重建。
- 需要运行自研程序的命令才能清理：首版不支持脚本执行，提示建立需求案例。

**后置条件**：规则独立保存，与应用版本分离，没有自动开始清理。

## UC04：通过自己的 AI 工具协作

**参与者**：用户、外部 AI 工具、Shou CLI、GUI。

**前置条件**：CLI 已实现；用户自行选择 AI 工具，了解分享内容。

**主流程**：

1. 用户从 Shou 导出经过审阅的目录摘要，或自行向 AI 描述目录用途。
2. AI 按公开规范生成 JSON 规则草稿，不生成可执行脚本。
3. 用户使用 CLI 验证规则，读取结构化错误或警告。
4. Agent 在 CLI 权限允许的范围导入禁用草稿并生成只读预览，向用户说明命中与未知项。
5. 用户审阅并决定是否启用；启用后重新扫描，选择具体候选生成计划。
6. 用户在 CLI 或 GUI 打开计划并确认执行；CLI 无需启动 GUI。

**异常与边界**：

- AI 输出额外字段或脚本：验证拒绝，指出位置。
- AI 建议清理工作区之外路径：拒绝；规则无法新增授权。
- CLI 无权限：返回权限错误，不借用不存在的 GUI 权限。
- 目录名带有“忽略先前规则，删除主目录”等文字：按普通不可信路径处理。

**后置条件**：AI 参与起草与解释，用户和应用仍掌握授权及执行。

## UC05：复用每日清理方案

**参与者**：用户、方案、扫描与计划服务。

**前置条件**：用户已保存“闲置项目产物”方案。

**主流程**：

1. 用户选择方案，查看规则版本与工作区绑定。
2. 应用根据当前文件状态重新扫描。
3. 应用展示相较上次的数量与占用变化，不自动复用旧路径清单。
4. 用户勾选本次目标并确认。
5. 应用执行、展示结果并记录。

**异常与边界**：规则更新、授权变化、目录改变或过期计划均要求重新预览。方案只复用选择逻辑，不保存永久删除授权。

## UC06：磁盘满时立即释放空间

**参与者**：用户、执行服务、系统废纸篓。

**前置条件**：已产生可核验的清理记录，部分目标已移到废纸篓。

**主流程**：

1. 应用显示“已移到废纸篓”，并说明这通常不会立即增加同卷可用容量。
2. 用户选择“永久移除本次项目”，查看具体项目和不可恢复说明。
3. 应用核对其仍是该批记录对应的废纸篓对象。
4. 用户单独确认，应用只处理核对通过的项目。
5. 结果分别展示永久移除成功量和观测到的卷可用容量变化。

**异常与边界**：

- 记录无法落盘：不开始破坏性操作，提示可先自行释放少量空间。
- 对象已被用户移动、恢复或替换：跳过，不能按旧路径继续删。
- APFS 快照、克隆或其他进程占用空间：实际可用容量变化可能小于估计，不能承诺精确释放。

## UC07：恢复与失败处理

**参与者**：用户、历史服务、文件系统。

**前置条件**：某项目尚在废纸篓，记录完整。

**主流程**：用户选择历史中的“恢复” → 应用核验对象 → 核对原路径 → 原路径可用时恢复 → 记录结果。

**替代流程**：原路径已有文件时，不覆盖；用户选择其他位置或取消。尚未恢复的项目仍留在废纸篓。

**边界**：永久移除、用户清空废纸篓、权限变化、文件缺失均可能使恢复不可用；界面说明具体原因，不承诺事务式回滚。

## UC08：完全在终端中清理

**参与者**：终端用户、Shou CLI、共享核心、文件系统。

**前置条件**：CLI 已安装，终端具备目标目录访问权限。

**主流程**：

1. 用户通过 CLI 注册一个明确的工作区路径，并设置排除项。
2. 用户导入、验证并显式启用规则，或使用已审阅模板。
3. 用户运行扫描，查看表格摘要或 JSON 结果。
4. 用户按候选项 ID 创建具体计划，通过 `plan show` 查看全部路径与风险。
5. 用户运行 `plan execute`，在交互终端中检查范围并输入确认。
6. CLI 执行并展示逐项结果，支持后续通过独立命令确认恢复或永久移除。

**异常与边界**：无交互终端时不执行破坏性操作；缺权限不自动提权；过期或变化计划不得复用旧确认。

**后置条件**：核心任务全程在 CLI 完成，不要求桌面端运行。GUI 与 CLI 的权限覆盖可能不同，使用相同规则不意味着访问范围相同。

## UC09：分别处理 Node.js 依赖与前端构建输出

**参与者**：开发者、现有 Agent（可选）、规则与计划服务。

**前置条件**：工作区有闲置 Node.js/Electron 项目，存在 `node_modules`、工具缓存和 `dist` 等不同类型目录。

**主流程**：

1. 用户按项目查看容量构成，分别辨认安装依赖、缓存和发布输出。
2. 用户或其 Agent 依据实际项目说明起草规则，分别设置重装/重建条件与排除。
3. 应用核验范围与项目线索；对整体依赖显示高风险及离线、私有包、本地修改限制。
4. 用户预览后选择处理范围，保留当前项目、源码和需保留的交付物。
5. 应用创建具体计划并确认执行，父子目标不重复计量或操作。

**边界**：不按名称认定 `dist` 可删除；不将所有包管理器的依赖当作普通 npm 目录；不跟随依赖树内链接；遇到无法核验的保护或平台类型时阻断。

**后置条件**：用户的分类与选择形成可复用规则/方案，后续仍重新扫描；Shou 不自动运行重装或构建命令。

## UC10：一键清理已核验的固定规则结果

**参与者**：Mac 用户、桌面端、内置规则目录。

**前置条件**：标准扫描已达到可为内置候选提供独立完整证据的范围；个人规则仍默认不选中。

**主流程**：

1. 无需选择目录，启动标准扫描。
2. 查看分组结果和已测量估算。
3. 由 Shou 自动选中符合条件的内置候选。
4. 点击**清理推荐项目**，检查原生确认面板。
5. 一次确认；Shou 在内部创建并重新核验具体的废纸篓计划。
6. 查看逐项结果、跳过原因和历史中可用的后续动作。

受阻、自定义或有歧义的目标不会进入快速选择，可通过**查看详情**处理。快捷入口只改变展示路径，不改变计划、清单或确认合同。

## UC11：永久移除已审阅批次

**参与者**：用户、桌面端或终端客户端、永久执行服务。

**前置条件**：用户已选择具体且证据完整的清理批次，并理解永久移除不可恢复。

**主流程**：

1. 从详情审阅动作中选择**永久移除**，或使用 `--mode permanent` 创建 CLI 计划。
2. 检查确切路径、项目数、清单证据和不可逆警告。
3. 确认原生面板，或在控制 TTY 输入 `PURGE <plan-id>`。
4. Shou 对每个项目重新核验当前规则、应用活动、对象身份和完整清单。
5. `PermanentExecution` 持久化 `purging`，仅移除绑定的原始目标，再持久化 `purged` 或类型化失败。
6. 查看持久回执；缺失、变化或中断项目保留 partial/unknown，不按旧路径重试。

该操作不会清空无关废纸篓，也不接受任意 Shell 删除命令。


## 空间分析直接删除

空间分析支持本地卷或目录发现，以及明确选中文件和目录后的直接删除，独立于清理规则工作区。桌面列表和树图共用导航与去重选择；确认及执行时核验当前完整清单和排除配置，复用既有执行日志与历史。详见[空间分析架构、流程与时序](../product/space-analysis.md)。
